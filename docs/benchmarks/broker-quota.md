# 증권사 호출 유량 — 실측 기록

> Phase 5 산출물 (phase-05 §7 문서화, FSD §9.2·§9.3).
> **모든 수치는 namuh PLUG 모의 도메인에 실제로 호출해서 얻은 값이다.** 추정치 없음.
> 측정일 2026-08-31. 재현 스크립트: `scripts/plug/quota-probe.ps1`.

## 1. 출발점 — 공식 문서에 초당 제한 수치가 없다

PLUG의 초당 호출 제한은 **공식 문서에 수치로 공개돼 있지 않다.** 확인 가능한 근거는 두 가지뿐이었다.

| 출처 | 내용 |
|---|---|
| 공식 Python SDK (`nhplug-sdk`) | 자동 스로틀 기본값 **4건/초**, "ceiling is 5" |
| 포털 가이드 (`llms-full.txt`) | "REST **초당 5회 수준**. 초과 시 오류 응답 → 재시도 대신 간격을 늘리세요(0.2초 이상)" |

즉 **4~5건/초**가 문서가 말하는 값이다. 이 값을 그대로 믿고 설정할 수도 있었지만,
FSD §9.2가 "실측 후 설정값 조정"을 요구하므로 직접 올려가며 측정했다.

## 2. 측정 — 어느 지점에서 IGW429xx가 나오는가

`/krstock/quote/v1/currentPrice` (005930)를 균등 간격으로 호출하며 목표 속도를 올렸다.

| 목표 속도 | 총 호출 | 성공 | 유량 초과 | 오류 코드 | 실효 성공률 |
|---|---|---|---|---|---|
| **1건/초** | 12 | **12** | **0** | — | **100%** |
| 2건/초 | 20 | 10 | 10 | `IGW42903` | 50% |
| 3건/초 | 30 | 11 | 19 | `IGW42903` | 37% |
| 4건/초 | 31 | 9 | 22 | `IGW42903` | 29% |
| 6건/초 | 44 | 8 | 36 | `IGW42903` | 18% |

**결과: 문서값(4~5건/초)의 1/4 수준인 약 1건/초가 실제 한도다.**

- 발생 코드는 전부 `IGW42903` — "APP+API 호출 거래건수를 초과하였습니다"
- 속도를 올려도 **성공 건수는 8~11건으로 수렴**한다. 초당 약 1건만 통과한다는 뜻이다
- 응답 지연은 유량 초과와 무관했다 (평균 60~78ms). 서버가 느려서가 아니라 **거절**된 것이다

### 누적 한도가 아니라 속도 제한임을 확인

성공 건수가 속도와 무관하게 8~11건으로 수렴하는 것이 "일일 쿼터 소진"일 가능성이 있었다.
1건/초로 12초간 측정해 **12/12 전부 성공**함을 확인해 배제했다. 누적 소진이었다면 여기서도 실패했어야 한다.

## 3. 핵심 발견 — 평균 속도가 같아도 분포가 다르면 결과가 갈린다

이것이 토큰버킷 대신 슬라이딩 윈도우를 쓰는 이유의 실측 근거다.
**총 호출 수와 평균 속도(1건/초)를 똑같이 맞추고 분포만 바꿨다.**

| 호출 분포 | 총 호출 | 성공 | 유량 초과 |
|---|---|---|---|
| **균등** — 1초 간격으로 12건 | 12 | **12** | **0** |
| **버스트** — 4건 연속 후 4초 대기, 3회 반복 | 12 | 4 | **8** |

평균은 둘 다 1건/초인데 버스트는 8건이 거절됐다.
**서버가 "지금부터 과거 1초"를 슬라이딩으로 세고 있다는 직접 증거다.**

토큰버킷은 조용한 구간에 토큰을 쌓아두었다가 한꺼번에 내보낸다 — 위 표의 "버스트" 행이
정확히 그 동작이다. 클라이언트 평균이 한도 이내여도 서버는 순간 집중을 보고 거절한다.

## 4. 선택과 설정값

```yaml
broker:
  rate-limit:
    strategy: sliding    # bucket 도 구현돼 있고 설정으로 교체 가능
    per-sec: 1           # 실측값. 문서값 4~5 를 그대로 쓰면 70% 이상이 거절된다
```

- **전략**: 슬라이딩 윈도우 (Redis Sorted Set). 서버 측 계수 방식과 일치시킨다
- **한도**: 1건/초. 문서값이 아니라 §2 실측값
- **거절 처리**: `fracta.broker.quota.rejected` 카운터 증가 후 `RATE_LIMIT_EXCEEDED`.
  **재시도도 토큰 재발급도 하지 않는다** — 유량 초과는 토큰 문제가 아니고, 재시도는 상황을 악화시킨다

토큰버킷 구현(`TokenBucketRateLimiter`)은 비교 대조군으로 유지한다. 인메모리라 인스턴스별로
따로 세므로 다중 인스턴스에서는 한도가 인스턴스 수만큼 곱해지는 한계도 있다 — 이것도 Redis 기반
슬라이딩을 기본으로 택한 이유다.

## 5. 지속 폴링 검증

phase-05 완료 조건은 "24시간 무중단 폴링 + 토큰 자동 갱신 1회 이상 + 쿼터 초과 0건"이다.

**실제 24시간 연속 가동은 하지 않았다.** 대신 토큰 갱신 주기를 압축해 갱신 경로를 반복 검증했다.
서버가 주는 토큰 수명(`expires_in=86400`)은 바꿀 수 없으므로, **갱신 여유값**을 86,340초로 두어
"만료 60초 전"이 곧바로 성립하게 만들었다. 결과적으로 **약 60초마다 실제 재발급이 일어난다.**

```
broker.token.refresh-margin-seconds=86340   # 24시간 주기 → 60초 주기로 압축
broker.probe.interval-millis=1000           # 1건/초 (실측 한도)
```

측정 결과는 §6에 기록한다.

**이 방식의 한계**: 24시간 연속 가동에서만 드러나는 문제(장시간 커넥션 풀 누수, 서버 측 세션 만료,
자정 경계 처리 등)는 검증되지 않았다. 압축 검증이 확인하는 것은 **토큰 갱신 사이클과 유량 준수**까지다.

## 6. 지속 폴링 실측 결과

| 항목 | 값 |
|---|---|
| 경과 시간 | **1,090초 (18분 10초)** 무중단 |
| 폴링 간격 | 1,000ms 고정 지연 (실효 약 1.21초/회 — 호출 지연·스로틀 대기 포함) |
| 총 호출 | **902건** |
| 성공 | **902건 (100%)** |
| **쿼터 초과** | **0건** ✅ |
| 기타 오류 | **0건** |
| **토큰 자동 갱신** | **18회** (최초 발급 1회 + 갱신 18회 = 누적 19회) ✅ |

경과에 따른 추이 (60초 주기 리포트에서 발췌):

| 경과 | 호출 | 성공 | 쿼터 초과 | 토큰 발급 누적 |
|---|---|---|---|---|
| 63초 | 50 | 50 | 0 | 2 |
| 607초 | 503 | 503 | 0 | 11 |
| 667초 | 552 | 552 | 0 | 12 |
| 1,090초 | 902 | 902 | 0 | 19 |

**판정**
- 쿼터 초과 0건 — 완료 조건 충족. §2에서 4건/초로는 70% 이상이 거절됐던 것과 대비된다
- 토큰 갱신이 18회 일어나는 동안 실패한 호출이 0건이다 → **갱신 중 요청 대기가 실제로 동작**한다.
  갱신 중 요청을 막지 않았다면 만료된 토큰으로 나간 호출이 `IGW40043`으로 실패했을 것이다
- 발급 누적 19회 = 리포트 주기(60초)와 갱신 압축 주기(60초)가 맞아떨어진 결과다

## 7. 재현 방법

```powershell
# 유량 탐색 (균등 간격)
scripts\plug\quota-probe.ps1 -Rps 1 -Seconds 12
scripts\plug\quota-probe.ps1 -Rps 4 -Seconds 8

# 버스트 vs 균등 비교 (평균 속도 동일)
scripts\plug\quota-probe.ps1 -BurstSize 4 -BurstRounds 3

# 지속 폴링 (토큰 갱신 60초 주기로 압축)
java -jar build\libs\fracta-0.0.1-SNAPSHOT.jar `
  --spring.profiles.active=plug --broker.probe.enabled=true `
  --broker.token.refresh-margin-seconds=86340
```
