## 3. 파티션 수와 처리량의 관계

종목 심볼 해시로 스레드를 고정하므로(`Math.floorMod`) **서로 다른 종목은 병렬로 처리된다.**

| 조건 | 실측 총 처리량 |
|---|---|
| 단일 종목 (파티션 1개만 사용) | 39.8 건/초 |
| 4개 종목 동시 (파티션 4개 사용) | **60.3 건/초** |

4배 종목인데 1.5배만 늘었다. 병렬화가 선형이 아닌 이유는 **병목이 오더북이 아니라 그 뒤의 원장**이기 때문이다.
원장 해시체인은 전역 `pg_advisory_xact_lock` 하나로 직렬화되므로(Phase 2 설계), 종목을 늘려도
결제 구간은 여전히 한 줄로 선다. 파티셔닝은 **매칭 경합**을 없애줄 뿐 결제 직렬화를 없애지 못한다.

## 4. 주문 경로가 초당 40건인 이유 — 그리고 왜 그대로 두는가

FSD §13.1의 "매칭 처리량 종목당 초당 100건"을 **매칭 엔진** 기준으로 보면 640,902건/초로 크게 충족한다.
반면 **결제까지 포함한 주문 경로 전체**는 39.8건/초다.

체결 1건이 하는 일:

| 작업 | 원장 advisory lock |
|---|---|
| `LedgerPort.unlock` (매도 잠금 해제) | 1회 |
| `LedgerPort.transfer` (증권 이전) | 1회 |
| 매수자 대금 차감 / 매도자 대금 지급 / 수수료 적립 | — |
| 주문 2건 체결량 반영 + 체결 기록 | — |

Phase 2 실측에서 원장 단건 append는 약 225 tps였다(`docs/notes/phase-02-ledger-notes.md`).
체결마다 append가 2회이므로 **원장만으로 이미 약 112 tps가 상한**이고, 여기에 대금 이동과
주문 갱신이 붙어 39.8 tps가 된다.

**그대로 두는 이유**: CLAUDE.md 절대 원칙 1이 "정합성 > 성능"이고, "성능을 이유로 advisory lock 제거"를
명시적으로 금지한다. advisory lock을 빼면 해시체인이 분기해 원장 자체가 무의미해진다.
따라서 한계를 여기에 기록하고 넘어간다.

### 실제로 한 최적화 (측정 기반)

처음 구현은 28.5 tps였다. 주문 1건이 트랜잭션을 6개 열고 있었다.

| 개선 | 내용 | 결과 |
|---|---|---|
| 결제+체결기록 병합 | 별도 트랜잭션 2개 → 1개 (`settleAndRecord`) | |
| 체결량 반영을 단일 UPDATE로 | 주문 2건 SELECT+UPDATE → UPDATE 2회 | |
| 종목 정보 재조회 제거 | 체결마다 조회 → 접수 시 1회 조회 후 전달 | |
| 지정가 주문의 불필요한 마무리 트랜잭션 제거 | 시장가일 때만 실행 | |
| **합계** | | **28.5 → 39.8 tps (+40%)** |

더 올리려면 원장 직렬화 자체를 손대야 하므로 여기서 멈췄다.

### 개선 여지 (구현하지 않음, 근거만 기록)

- **토큰 심볼별 체인 분리**: 종목마다 별도 해시체인이면 advisory lock도 종목별로 갈라져
  파티션 병렬화가 결제까지 이어진다. Phase 2에서 "전역 감사(단일 seq 스캔)가 복잡해진다"는
  이유로 보류했다(`docs/notes/phase-02-ledger-notes.md`).
- **체결 배치 기록**: 한 주문이 N건을 체결할 때 원장 append를 묶으면 lock 획득이 N회 → 1회가 된다.
  다만 부분 실패 처리가 복잡해진다.

## 5. `SUSPENDED` 시 미체결 주문 처리 정책

**정책: 미체결 주문 전량 취소 + 잠금 해제.**

괴리율이 20%를 넘어 종목이 자동 정지되면(TR-08), 그 종목의 `OPEN`/`PARTIALLY_FILLED` 주문을
모두 취소하고 매도 잠금을 푼다.

**근거**
1. 거래 중단은 "이 종목의 거래를 멈춘다"는 뜻이다. 주문을 남겨두면 재개 시점에 의도치 않은
   가격으로 체결될 수 있다 — 정지 사유가 가격 이상이었는데 그 가격의 주문을 살려두는 건 모순이다.
2. **잠금이 영구히 남는 걸 막는다.** 매도 주문은 원장 `locked_units`를 잡고 있다. 주문만 방치하면
   투자자는 자기 보유분을 영원히 쓸 수 없다 (phase-06 §흔한 실수 9).
3. 취소는 되돌릴 수 있지만(재주문) 잘못된 체결은 되돌릴 수 없다.

**구현 주의**: 이 정리는 매칭 파티션 스레드 **밖에서** 실행한다. 안에서 호출하면 같은 파티션을
다시 잡으려다 스레드가 자기 자신을 기다려 교착한다(구현 중 실제로 만든 뒤 고쳤다).

## 7. 구현 중 발견해 고친 정합성 버그

측정과 테스트가 아니었으면 놓쳤을 것들이다.

1. **투자자 잔액 lost update** — KYC Mock이 가입 3초 뒤 `investor` 행의 `kyc_status`만 바꾸는데
   JPA가 **행 전체를 UPDATE**하면서, 그 사이 확정된 매매 대금을 로드 시점의 낡은 잔액으로 덮어썼다.
   INV-6이 정확히 −3,000원(1,000원 × 3계정) 어긋나 발견했다. `@DynamicUpdate`로 변경된 컬럼만
   쓰도록 고쳤다. **돈이 사라지는 버그였다.**
2. **결제 실패 시 오더북과 DB 불일치** — 결제가 롤백돼도 인메모리 오더북의 잔량은 줄어든 채 남아
   실제보다 적은 물량만 남았다. 결제 실패 시 체결을 되돌리고 큐에서 빠진 주문을 되돌려 놓게 고쳤다.
3. **수수료가 사라지던 문제** — 매수자에게서 뺀 수수료를 받는 곳이 없어 INV-6이 수수료만큼 깨졌다.
   플랫폼 수수료 계정을 두어 금액이 보존되게 했다.
