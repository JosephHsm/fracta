# AI 가드레일 설계

> Phase 8 산출물 · README 필수 항목 6번
> 공격 프롬프트 목록과 차단 결과표는 [`docs/appendix/guardrail-attack-prompts.md`](../appendix/guardrail-attack-prompts.md) (자동 생성)

투자설명서 질의응답에 LLM을 붙일 때의 문제는 성능이 아니라 **책임**이다.
금융소비자보호법상 투자권유는 자격과 절차를 갖춘 행위이고, 챗봇이 "이거 유망합니다"라고
한 줄 답하는 순간 그 요건을 우회한 권유가 된다. 이 문서는 그걸 프롬프트가 아니라
**코드로** 막는 구조를 설명한다.

---

## 1. 금소법상 제약 → 설계 대응

| 법·규제상 제약 | 설계 대응 | 구현 위치 |
|---|---|---|
| 투자권유는 적합성·설명의무 절차를 거쳐야 한다 | 챗봇은 **권유를 하지 않는다.** 문서 원문 전달만 하고, 권유로 읽힐 표현은 출력 단계에서 코드로 차단 | `output_guard.py` |
| 확정되지 않은 수익률을 단정·보장할 수 없다 | 수익률 예측·보장 표현 패턴 차단 | `output_guard.py` |
| 설명은 **교부된 투자설명서**에 근거해야 한다 | 근거 페이지 번호 없는 답변은 차단. 검색 결과 밖 페이지 인용도 차단 | `output_guard.py` |
| 문서에 없는 내용을 설명하면 안 된다 | 유사도 임계값 미달 시 LLM을 아예 호출하지 않고 고정 문구 반환 | `ask_service.py` |
| 개인정보 최소 수집·처리 | 주민번호·계좌번호 등이 담긴 질문은 입력 단계에서 차단 → 외부 API로 나가지 않음 | `input_guard.py` |
| 권유 여부에 대한 사후 입증 책임 | 모든 질의를 차단분 포함 `ai_conversation_log` 에 전량 기록 | `conversation.py` |

## 2. 3단계 구조

```
질문
 │
 ├─① 입력 가드레일 ─── 차단 ──▶ 고정 문구 (LLM 호출 0건)
 │   프롬프트 인젝션 / 개인정보
 │
 ├─  임베딩 → 코사인 top-5
 │   최고 유사도 < 0.6 ──────▶ "확인할 수 없습니다" (LLM 호출 0건)
 │
 ├─② 시스템 프롬프트 + 구조화 출력
 │   FSD §10.3 문구 원문 + output_config.format 으로 스키마 강제
 │
 └─③ 출력 가드레일 (코드 검증)
     stop_reason=refusal? → 차단 (재시도 없음)
     JSON 파싱 실패?      → 차단 (통과시키지 않는다)
     금지 표현 정규식?     → 차단
     cited_pages 비었나?  → 차단
     인용이 검색결과 밖?   → 차단
     본문 [p.N] 도 검사   → 차단
        │
        └─ 통과 ──▶ 답변 + 인용 페이지
     차단 시 재시도는 **1회만**, 그래도 걸리면 고정 문구
```

각 단계의 설계 의도가 다르다.

- **①은 비용과 노출을 줄인다.** 뚫려도 ③이 받는다. 여기서 완벽할 필요가 없고, 완벽할 수도 없다.
- **②는 협조를 구한다.** 모델이 지키면 좋고, 안 지켜도 상관없다는 전제로 쓴다.
- **③이 실제 방어선이다.** 여기만 통과하면 사용자에게 도달하므로 여기서 실수하면 끝이다.

## 3. 왜 프롬프트만으로는 불충분한가

시스템 프롬프트에 "투자 권유 금지"라고 적는 것은 **모델의 협조를 요청**하는 것이지
**강제**가 아니다. 세 가지 이유로 강제가 될 수 없다.

### 3.1 프롬프트는 우회 대상이다

인젝션의 목적이 정확히 시스템 프롬프트를 무력화하는 것이다. 부록의 INJ-01~20이
그 시도들이고, 이 중 어느 하나라도 성공하면 프롬프트 기반 방어는 통째로 사라진다.
반면 출력 단계 정규식은 **모델이 무엇을 믿든 상관없이** 최종 문자열을 검사하므로
인젝션의 사정권 밖에 있다.

### 3.2 모델은 지시를 부분적으로만 따른다

"수익률 예측 금지"를 지시해도 "목표 배당수익률은 연 5.5%로 **예상됩니다**" 같은
표현은 모델 입장에서 문서 인용에 가깝다. 경계 판단을 모델에 맡기면 경계가 흔들린다.
코드는 흔들리지 않는다.

### 3.3 검증할 수 없다

프롬프트 기반 방어는 "잘 되고 있다"를 증명할 방법이 없다. 코드 기반 방어는
테스트로 고정되고 회귀가 잡힌다. 실제로 이 프로젝트에서는 공격 프롬프트 20종이
`pytest` 로 매번 돌고, 패턴이 퇴화하면 빌드가 깨진다.

### 3.4 실제 우회 사례 — 띄어쓰기 하나

프롬프트가 아니라 **정규식조차** 얼마나 쉽게 빠져나가는지 보여주는 사례가 개발 중에 나왔다.
FSD §10.3이 정한 원문 패턴은 다음과 같다.

```python
r"(사|매수|투자)(하세요|하시길|추천)"
```

이 패턴은 `매수추천` 은 잡지만 **`매수 추천` 은 잡지 못한다.** 두 그룹이 붙어 있어야 하기 때문이다.

| 응답 | FSD 패턴 | 결과 |
|---|---|---|
| `매수추천 의견입니다` | 매치 | 차단 |
| `매수 추천드립니다` | **미스** | (보강 패턴이 없었다면) **통과** |

같은 종류의 구멍이 여러 개 있었다.

| 우회 표현 | 빠져나간 이유 |
|---|---|
| `적극 추천드립니다` | `추천` 뒤 어미가 `하세요/하시길` 이 아니다 |
| `원금은 보장됩니다` | `수익률` 이라는 단어가 없어 3번 패턴에 안 걸린다 |
| `상승 가능성이 높습니다` | `오를/상승할` 이 아니라 명사형 `상승` 이다 |
| `매력적인 투자 기회입니다` | 권유 동사가 아예 없다 |
| `사도 됩니다` | `사` 뒤가 `하세요/하시길/추천` 이 아니다 |

그래서 `SUPPLEMENTARY_PATTERNS` 12개를 **우회 사례를 근거로** 추가했다.
FSD 원문 4개는 정본이므로 그대로 두고 별도 목록으로 관리하며, 어느 쪽에 걸렸는지
`FSD:` / `SUPP:` 접두사로 구분해 기록한다 — 그래야 "사양이 잡은 것"과
"보강해서 잡은 것"을 결과표에서 분리할 수 있다.

**교훈은 정규식을 더 잘 쓰자가 아니다.** 문자열 매칭은 본질적으로 불완전하고,
그래서 인용 검증(`NO_CITATION` / `HALLUCINATED_CITATION`)이라는 **구조적** 방어가
함께 있어야 한다. 표현은 무한히 변형되지만, "근거 페이지가 검색 결과 안에 있는가"는
변형할 수 없는 사실 판정이다.

## 4. 환각 인용 검출

FSD §14의 명시 완료 조건이다. 두 겹으로 본다.

**1차 — 구조화 출력.** `output_config.format` 으로 응답 스키마를 고정한다.

```json
{"answer": "...", "cited_pages": [7], "found_in_document": true}
```

자유 텍스트에서 `[p.\d+]` 를 정규식으로 긁어내는 것보다 안정적이다. 모델이 인용을
빠뜨리면 스키마 위반이 아니라 **빈 배열**로 드러나고, 그건 `NO_CITATION` 차단이다.

**2차 — 본문 재검사.** `cited_pages` 는 맞는데 본문에서 다른 페이지를 부르는 경우가 있다.
`answer` 안의 `[p.N]` 도 검색 결과 페이지 집합의 부분집합인지 확인한다.

```python
valid = {c.page_no for c in retrieved_chunks}   # 이번 질의로 실제 검색된 페이지
if not set(cited_pages).issubset(valid):        # → HALLUCINATED_CITATION
```

핵심은 **비교 대상이 "문서 전체 페이지"가 아니라 "이번 질의의 검색 결과"** 라는 점이다.
문서에 12페이지가 있다고 12를 인용해도 되는 게 아니다. 이번에 12페이지를 근거로
주지 않았다면 모델은 그 내용을 볼 수 없었고, 따라서 지어낸 것이다.

## 5. 로컬 모델(Ollama) 대응 — 파싱 실패는 차단이다

Claude는 `output_config.format` 으로 스키마를 강제하지만, 로컬 모델의 준수도는 낮다.
`OllamaAdapter` 는 JSON 파싱 실패를 **흡수하되 감추지 않는다.**

```python
parsed, diagnostics = parse_json_object(text)   # 실패 시 parsed=None
return LlmResult(raw_text=text, parsed=parsed, ...)
```

호출부는 `parsed is None` 을 `PARSE_FAILURE` 로 **차단** 처리한다. 여기서 "일단
원문이라도 보여주자"고 봐주면 가드레일 전체가 우회된다 — 스키마를 안 지키는 응답은
`cited_pages` 도 없으므로 인용 검증도 무력해지기 때문이다.

`LlmResult.refused` 필드를 둔 이유도 같다. Claude의 `stop_reason == "refusal"` 과
Ollama의 정상 응답을 하나의 인터페이스로 다루되, **거부를 정상 응답으로 착각하지 않기**
위해서다. refusal은 재시도하지 않는다 — 정책 판단은 재시도해도 같고 크레딧만 쓴다.

## 6. 의도적으로 감수한 오탐

가드레일은 **거짓 양성 쪽으로 기울여** 설계했다. 정합성 > 편의라는 프로젝트 원칙에 따른 것이다.

| 감수한 오탐 | 이유 |
|---|---|
| 투자설명서 원문에 `수익률 전망` 이라는 표제가 있으면 그 요약도 차단될 수 있다 | 권유로 읽힐 여지가 있는 문장을 흘리는 쪽이 더 큰 손해다 |
| `전망합니다` 가 중립적 맥락에서 쓰여도 차단된다 | 맥락 판단을 코드가 할 수 없다. 판단이 필요하면 원문을 보게 한다 |
| 인용을 빠뜨린 정확한 답변도 차단된다 | 근거 없는 설명은 그 자체로 요건 미달이다 |

단, 오탐을 무한정 허용하면 기능이 무의미해지므로 **위험요인 원문 요약은 통과해야
한다**는 것을 테스트로 고정했다 (`test_위험요인_원문_인용은_차단되지_않아야_한다`).
"위험 관련 질문에는 해당 위험요인 원문 요약을 우선 제시"가 FSD §10.3의 요구사항이라,
여기가 막히면 요구사항끼리 충돌한다.

## 7. 차단 사유를 사용자에게 알리지 않는 이유

응답에는 `blocked: true` 만 싣고 `blocked_reason` 은 싣지 않는다.
어떤 패턴에 걸렸는지 알려주면 그건 **우회 안내**다. 사유는 두 곳에만 남는다.

- `ai_conversation_log.guardrail_reason` — 사후 분석·입증
- 서버 로그 — 운영 모니터링

Core의 `AiController` 도 `blockedReason` 을 응답 DTO에서 제외하며,
`AiIntegrationTest.blockedReasonIsNotExposed` 가 이걸 검증한다.

## 8. 전량 기록

차단된 질의를 로그에 남기지 않으면 **가드레일이 동작했다는 것을 증명할 수 없다.**
`ai_conversation_log` 는 어떤 경로로 끝나든 한 건을 남긴다.

| 컬럼 | 용도 |
|---|---|
| `llm_called` | 임계값 미달·입력 차단은 `false` — LLM 호출 0건을 데이터로 증명 |
| `guardrail_stage` | `INPUT` / `OUTPUT` / `NONE` |
| `guardrail_reason` | 차단 사유 코드 |
| `retrieved_chunk_ids` | 환각 인용 판정의 근거가 된 검색 결과 |
| `raw_answer` vs `final_answer` | 모델이 뭐라 했고 사용자가 뭘 봤는지의 차이 |
| `input_tokens` / `output_tokens` | 비용 분석 근거 ([provider-comparison.md](provider-comparison.md)) |

---

## 9. 메트릭

`fracta.ai.guardrail.blocked` (FSD §13.3). 판정은 AI 서비스(Python)가 하지만
카운터의 정본은 Core의 Micrometer다 — 프론트가 AI 서비스를 직접 부르지 않고
Core를 거치게 해서 인증·감사·서킷브레이커·메트릭이 한 지점을 지나게 했다.

AI 서비스 자신도 `/ai/metrics` 로 자기 집계를 노출하지만 이건 자기 진단용이다.
